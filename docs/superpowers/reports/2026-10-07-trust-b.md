## F19 (D26) — `mergeSpeakers` is one transaction with `edits` rows. Commit `d1276df`

- **What.** The JS DB layer had no transaction primitive (each `Storage.query` is one statement), so
  a native one was added: `Storage.transaction(statementsJson)` → `StorageModule.transaction` →
  `AudioDb.runTransaction` (`beginTransaction` / `setTransactionSuccessful` / `endTransaction`).
  `mergeSpeakers` sends four statements in one call, in this order: (1) `INSERT OR REPLACE` a
  `'speaker'` edit for every line currently on the dropped speaker (so `SpeakerRepair` keeps the
  merge, and the kept speaker counts as protected); (2) repoint any earlier hand assignment to the
  dropped speaker at the kept one (else `reapplicable` discards it); (3) move the lines; (4) delete
  the speaker. Spec, `jest.setup.js` stub and `queries.ts` (`mergeSpeakers` only) changed.
- **Tests** (`src/db/__tests__/mergeSpeakers.test.ts`, real DDL via `node:sqlite`): both effects
  apply together and another meeting is untouched; edit rows exist for exactly the moved lines; an
  older edit is repointed; a trigger that aborts the final DELETE rolls back the first three; one
  transaction call and no bare queries.
- **Mutants (killed, restored).** back to bare queries (2 fail); edits INSERT selecting nothing;
  no repoint; no DELETE (2 fail).
- **Limit of the proof.** The jest stand-in for `transaction` implements the contract
  (BEGIN/COMMIT/ROLLBACK); it proves the SQL and that `mergeSpeakers` uses the one call, NOT that the
  Android SQLCipher handle rolls back. Device-only. `src/db/schema.ts` still lacks the `edits`
  table (it is only in `AudioDb.SCHEMA`); the test carries its own copy of that DDL. Not fixed here.

- **(f) D16 first line missing. Commit `f7db065` (log line only; exclusion behaviour unchanged).**

  *Investigation note.* The lag is `verdict.lagFrames * 10` ms (clip start in the capture, 10 ms
  resolution). `AnnouncementSpan.exclude` cuts `[lag - 500, lag + clipMs + 500]` out of the VAD spans
  (clipMs about 4505 ms; so with the clip landing at 350 ms the cut is `[-150, 5355]` ms). A span
  entirely inside the cut is dropped; one overlapping it keeps a remainder only if at least 250 ms
  long. So any speech that begins in the first about 5.4 s is lost up to 5355 ms: a person who says
  "Good morning everyone." (about 2 s) while the clip is still playing, or in the half-second after
  it, loses it from the ASR input. If VAD joins clip and speech into one span, the span is trimmed to
  start at 5355 ms. Mic recordings with the announcement on are exactly the case; imports are not
  affected (no lag). The audio and `announced_at` are untouched, so playback still has the words; only
  the transcript is missing them. `a351194` widened the exclusion to every FOUND clip, so it can only
  have removed more. This is the leading hypothesis, not a confirmed cause (no phone recording was
  available): a recording whose first line starts after about 5.4 s would not be explained by it.
  *Diagnostic shipped:* `ProcessingEngine.announcementFree` now always logs the lag, clip length, cut
  bounds, span counts, and the first VAD span start before and after
  (`adb logcat -s AudioPipeline | grep "announcement at"`). Next step: one mic recording with the
  clip on, and compare "first span starts X -> Y" against when the first word was spoken.
